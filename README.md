# 本地书架（book-manager）

纯离线、单用户的桌面端个人图书管理工具。无任何网络请求、无账号体系，所有数据（SQLite 单文件 + 封面 / 附件）都在本机。

## 技术栈

| 层    | 选型                                 | 说明                                       |
| ---- | ---------------------------------- | ---------------------------------------- |
| 桌面容器 | Electron 44                        | Windows / macOS 兼容                       |
| 前端   | React 19 + TypeScript 5.8 + Vite 7 | 每页一个文件夹（代码 + `.less`），根节点唯一作用域类          |
| 构建   | electron-vite 5                    | main / preload / renderer 三目标一次构建        |
| 数据库  | better-sqlite3 13                  | 同步 API；WAL 模式；库文件在 `userData/library.db` |
| 样式   | Less 4                             | 全局变量在 `src/renderer/styles/global.less`  |

> 版本决策备注：TypeScript 锁 5.8（不追 7.0 原生编译器，`tsc -b` 兼容性优先）；Vite 锁 7（electron-vite 5 的 peer 只支持到 7）。

## 跑起来

前置条件：**Node.js >= 20.19.0**（`@electron/rebuild` 4.x 与 electron-vite 5 都要求 Node 20+；Node 18 会在 rebuild 阶段报 `node:util does not provide an export named 'styleText'`）。本机用 nvm 的话：`nvm use 24.20.0`。

```bash
npm install          # 安装依赖
npm run rebuild      # 为 Electron ABI 重编译 better-sqlite3（必做，见下）
npm run dev          # 开发模式（热更新）
```

生产构建与预览：

```bash
npm run build        # 产出 out/{main,preload,renderer}
npm run preview      # 以生产产物启动
```

### 两个本机环境注意点

1. **`npm run rebuild` 其实可以跳过（留着当保险）**：老版本 `better-sqlite3` 是 node-gyp 编出来的、跟 ABI 绑死（Node 127 / Electron 149 不通用），现在 v13 发布的是 N-API 的 `prebuilds/<平台>-<架构>.node`，同一份文件实测在 Node 22（ABI 127）和 Electron 44（ABI 149）下都能加载。打包后的程序跑起来数据库正常，用的就是这份没重编译的二进制。真出 "compiled against a different Node.js version" 再跑 `npm run rebuild`（需要 VS C++ 工具链 + Python 3）。
2. **Node 版本**：若报 `node:util does not provide an export named 'styleText'`，说明终端里是 Node 18（`node -v` 确认），`nvm use 24.20.0` 切换后重跑。
3. **公司 Nexus 镜像下 rollup 原生模块**：镜像偶发不传递 `@rollup/rollup-win32-x64-msvc` 这个可选依赖，已作为显式 devDependency 钉死在 `package.json`（版本与 rollup 对齐）。若换机器重装后构建报 `Cannot find module '@rollup/rollup-win32-x64-msvc'`，手动 `npm i -D @rollup/rollup-win32-x64-msvc@<rollup版本>` 即可。
4. **Electron 二进制下载慢**时，可用镜像：`ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node node_modules/electron/install.js`。

## 应用图标

`resources/` 里是从一张 SVG 导出的一整套图标，`scripts/make-icon.js` 负责导出（换图时重跑即可）：

| 文件 | 用途 |
|---|---|
| `icon.svg` | 源文件，改图从这里改 |
| `icon.png` | 1024×1024，留给以后打包 macOS 时生成 icns |
| `icon-256.png` | 非 Windows 平台的窗口图标 |
| `icon.ico` | Windows 窗口 / 任务栏 / 标题栏图标，内含 **16 / 24 / 32 / 48 / 64（32 位 DIB）+ 128 / 256（PNG）** 七档，任务栏取 16/24/32 时是原生尺寸不会发虚 |
| `public/favicon.svg` | 页面级图标（调试/预览时的标签页） |

主进程 `createWindow()` 里通过 `?asset` 导入（electron-vite 会解析成运行时绝对路径，`out/main/index.js` 里落成 `join(__dirname, '../../resources/icon.ico')`），Windows 走 ico、其余走 png，**解码为空时自动退回另一份**。另外 `app.setAppUserModelId('com.bookmanager.app')` 让 Windows 把窗口归到同一个应用下，任务栏不会另起一组。

换图标：

```bash
npm i -D playwright-core    # 只在本机装一次（光栅化走系统 Edge，不下载 Chromium）
node scripts/make-icon.js "path/to/icon.svg"
```

脚本会先扫出图形的真实不透明边界再居中，四周留 8% 边距——原图里 path 常常超出 viewBox（这张图标底部就溢出 32px），直接铺满会被裁掉一截、整体还偏上。

第 64 行那句「以后接 electron-builder」已经落地了：`win.icon` 就是 `resources/icon.ico`，`appId` 与 `app.setAppUserModelId` 都是 `com.bookmanager.app`。

## 打包成 exe

```bash
npm run dist        # 出安装包 + 免安装版
npm run dist:dir    # 只出 dist/win-unpacked（改完想快速双击验证时用）
```

产物在 `dist/`：

| 文件 | 用途 |
|---|---|
| `本地书架-0.1.0-安装包.exe` | NSIS 安装向导：可选安装目录、建桌面与开始菜单快捷方式、带卸载程序 |
| `本地书架-0.1.0-免安装.exe` | 单文件绿色版，双击即用。**每次启动都要把 ~200MB 解压到 `%TEMP%`**，实测首次到窗口出现要半分钟左右（杀软扫描还会更久），适合拷给别人临时用，不适合天天开 |
| `win-unpacked/` | 未压缩的应用目录，`本地书架.exe` 直接可跑，调试用 |

版本号取 `package.json` 的 `version`，产物名跟着变。**想发第二版**就改 version 再 `npm run dist`。

配置全在 `electron-builder.yml`，几个点和背后的原因：

- **`productName: 本地书架`，但主进程第一行 `app.setName('book-manager')`**。`app.getPath('userData')` 默认取应用名，不钉死的话装完第一次启动会去 `%APPDATA%\本地书架` 建一个空库——用户看到的是「书全没了」。名字只管显示（窗口标题、快捷方式），数据目录必须和开发版共用 `%APPDATA%\book-manager`。
- **`asarUnpack: node_modules/better-sqlite3/**`**。`.node` 二进制在 asar 里没法 `dlopen`，漏了这条启动就报 `Cannot open better_sqlite3.node`。解出来落在 `resources/app.asar.unpacked/`。
- **`npmRebuild: false` + `rebuild` 脚本改 `-o better-sqlite3`**。electron-builder 默认会把 `node_modules` 里**每个**原生模块都编一遍，而 `pdfjs-dist` 的 optionalDependency `canvas` 需要 cairo / GTK 那一堆库，本机没有就死在 `无法打开包括文件: cairo.h`，整个打包中断。原来的 `-w better-sqlite3` 不过滤（它还要配合 `--types`），得用 `-o`（only）。
- **`files` 只列 `out/` 与 `package.json`**。默认策略会把整个项目目录塞进 asar，根下几十张 `shot-*.png` 截图、探针脚本、`identifier.sqlite` 全得跟着走。
- **`deleteAppDataOnUninstall: false`**。卸载默认连书库和备份一起删——那是几年的东西，绝不能。
- `perMachine: false`：装到当前用户目录（`%LOCALAPPDATA%\Programs\本地书架`），不用管理员权限。

首次打包要联网拉 Electron 的 zip 和 NSIS 工具链。国内慢就加两个镜像：

```bash
export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
export ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/
```

没配代码签名证书，`本地书架.exe` 是未签名的，**别的机器上第一次运行会弹 SmartScreen「Windows 已保护你的电脑」**，点「更多信息 → 仍要运行」即可。自己留着用不用管。

打包前后数据完全不受影响：程序读的一直是 `%APPDATA%\book-manager\library.db`，安装版、免安装版、`npm run dev` 三份共用同一个库（别同时开两个就行，SQLite 会锁）。

## P0 已实现（本次交付）

- **数据库**：10 张表一次建齐（P1-P4 复用），软删除 `is_deleted`、级联删除子表、`update_time` 触发器
- **分类管理**：无限层级树、含子类图书计数、新增 / 编辑 / 删除守卫（有子分类或有图书时拒绝并提示）、同级拖拽排序（跨级拒绝）、防成环
- **图书**：手动录入全字段（书名 / 作者 / 出版社 / 出版日期 / ISBN / 页数 / 定价 / 语言 / 馆藏位置 / 购入日期 / 分类 / 阅读状态 / 评分 / 已读页数 / 短评 / 简介）、编辑、软删除
- **浏览**：书架封面网格（无封面按书名哈希生成确定性渐变占位）+ 列表表格双视图、列排序、阅读状态角标（`unread` 未读为默认态、不显示角标；`want` / `reading` / `read` 才出徽标）
- **检索**：全局关键词（书名 / 作者 / ISBN / 出版社 / 简介，200ms 防抖）、分类树含子类筛选、状态筛选、10 种排序
- **回收站**：列表、单本恢复、全部恢复、单本彻底删除（级联删本地文件）、清空（均二次确认）
- **首页**：统计卡片（总藏书 / 未读 / 想读 / 在读 / 已读 / 无封面）、最近添加、分类快捷入口
- **布局**：左侧导航（分类树 + 书单占位 + 回收站计数）、顶部搜索 + 视图切换 + 录入入口

- **数据库迁移**：`book` 增加 `ebook_path` / `source` 列，新增 `settings` 键值表；迁移继续走 PRAGMA table_info 判重 + ALTER

## 大文件性能（实测，7.1 MB / 248 万字 / 4.07 万段）

同一台机器、同一份文本，用系统 Edge 跑构建产物：

| 指标 | 全量渲染（旧） | 虚拟滚动（现） |
|---|---|---|
| 首屏建 DOM + 排版 | 413~886 ms | ~100 ms |
| 改一次字号的重排 | 328~465 ms | 12~26 ms |
| DOM 里的 `<p>` 数量 | 40667 | 12~17 |
| 连续滚动每屏 JS 开销 | — | ~4 ms |

正确性一并验过：滚到中间 50%、滚到底 100%、目录跳到第 11 章落到「第11章 风起于青萍之末」、退出后重开恢复到 37%、改字号前后位置保持在 50%、上下各连续滚 30 屏 DOM 稳定在 12 段。

已知代价：**从未访问过的区域靠估算定位**，所以拖动滚动条一次跳到远处会有 1~5% 的位置偏差，滚一屏之后即自我校正（实测区会被实测高度永久覆盖）。这是虚拟滚动的固有取舍，不影响「显示百分比 = 当前可见内容的位置」这条语义。

## R2 已实现（PDF 阅读）

PDF 走的是完全不同的渲染路径，但共用同一个外壳与同一条进度链路：`ReaderBook` 只是把「正文文本」换成了「原始字节 + 页数」。

- **按页渲染**：pdfjs 3.11 逐页画到 canvas，只画视口附近那几页，离开视口 4 页以外的画布直接释放。实测 358 页的书全程只维护 3~7 张画布，几百页扫描件不会把内存吃满
- **文本层**：每页叠一层透明文字，可选中、可复制、Ctrl+F 能查找；`--scale-factor` 必须写在页容器上，缺了 pdfjs 会把文字层摊到左上角并刷警告
- **目录**：取 PDF 自带大纲（bookmark），目的地解析成页码后压平，层级用全角空格缩进；扫描件「每页一条 000001.bmp」这种假目录会被过滤，剩不到两条就当没有（此时隐藏目录按钮，靠底栏页码跳转兜底）
- **页码**：底栏「第 [n] / 总页 页」，输入页码回车即跳；PageUp/Down 与空格按页翻
- **缩放**：适应宽度 / 100% / 150% / 200%。100% 按 96dpi 折算（1pt = 4/3 px），不折算的话 100% 比「适应宽度」还小，看起来像缩小了
- **进度**：`locator` 存页码（`{"k":"page","v":67}`），`percent` 按「页内位置」折算，滚到底正好 100%；`book.current_page` 仍是 percent × pages 反算，书架与时间线零改动
- **worker 用 blob 起**：`?raw` 把 worker 内联成字符串再转 blob URL —— 打包后页面在 `file://` 下，直接指向磁盘的 worker 脚本会被同源策略挡掉
- **CMap 内联**：169 个 `cmaps/*.bcmap`（约 1.5MB）以 base64 打进包，配自定义 `CMapReaderFactory` + `useWorkerFetch: false`。不做这件事，中文 PDF 会整页文字空白或乱码（默认实现让 worker 去 fetch 本地文件，file:// 下必然失败）。pdfjs / worker / cmaps 全部动态引入，不打开 PDF 不会加载
- **跳页不做平滑滚动**：动画途中按需渲染会改布局，Chromium 会中断动画 —— 实测一次跳 200 页会停在中途差两百多像素，页码跟着报错。瞬时跳转没有这个问题
- 冒烟新增 `[26]` 14 项（打开返回字节流、页数取自文件、无大纲时目录为空、页码 locator 往返、页数补齐边界、损坏 PDF 与暂不支持格式各自抛错），合计 **329 项**

## R3 已实现（EPUB 阅读）

EPUB 又是第三条路径，但依然共用同一个外壳与同一条进度链路：主进程只给「小节规模 + 目录」，正文按节现取现解压，渲染层用沙箱 iframe 承载。

- **按节取正文**：`reader:section` 一次给一节（xhtml + CSS + 图片全内联）。一本 12 MB 的图文 EPUB 展开后正文加图能到几十 MB，整本过 IPC 只为读第三章纯属浪费内存
- **样式与图片内联**：`<link rel=stylesheet>` 的整份 CSS 读进来，`url()` 与 `<img src>` 改写成 data URL（上限 12 MB/张），`@import` 直接删掉。所以 iframe 里零网络请求，`file://` 下也不会有「图片全裂」
- **两层去脚本**：主进程删掉 `<script>` / `<iframe>` / `on*` 事件属性 / `javascript:` 协议 / `<link>` `<base>`，iframe 再挂 `sandbox="allow-same-origin"`（不给 `allow-scripts`）兜底。`allow-same-origin` 留着是为了量高度
- **多节拼接的连续滚动**：相邻几节纵向排进同一个滚动容器（当前节前 2 后 3），滚过章节边界就是正常的段落间隔，不用在节末再按一次键。窗口滑动有三条硬规矩：**先扩后缩**（新节挂上并量到高度之前不收旧节，否则内容骤矮、浏览器把 `scrollTop` 夹走，正在读的那行会往上跳）、**锚点补偿**（换窗口前后钉住某一节的视口偏移，而不是把移除的高度加起来硬减——后者在跳章时必翻车）、**落位要回报结果**（目标节下面的内容还没高度时 `scrollTop` 会被夹住，得等下一轮再接）
- **外层统一滚动**：iframe 高度 = 内容 `scrollHeight`，滚动的永远是外层 `.reader-scroll`。滚轮在内层被接管后转给外层，键盘（PageUp/Down、Esc、+/-、t）在焦点落进 iframe 时转一份回父窗口 —— 用户不该因为换了个格式就发现「滚轮没反应」
- **进度按字数加权**：一节的字数是权重，`percent = (前面各节字数 + 本节字数 × 节内比例) / 全书字数`。按节数平均会偏得很离谱：实测某本书的「致谢」只有 6 个字却独占一节，按节数算就是 1/28 = 3.6%，按字数算才是 0.003%。**纯图小节**（扉页、整页插图、漫画）字数为 0，按图数给一个基准权重，否则图多的书滚几屏进度条都不动
- **资源找不到就换成透明占位**：书里引用了已被删掉的装饰图（真实样本里 `styles/Images/bq.jpg` 就是）时，`url()` 不能原样留着——srcdoc 会按应用自己的地址去请求，控制台一片 404，还等于偷偷发了网络请求。zip 内路径查找还带大小写兜底（书里写 `Images/x.png`、包里是 `images/x.png` 很常见）
- **定位**：`locator` 存 `{"k":"section","v":52.45}`（第 52 节读了 45%），是三种格式里唯一带小数的。`total+1` 表示「最后一节读到底」，重开时按 `(total, 1)` 还原，否则读到 100% 退出再打开会掉回 99%
- **目录**：EPUB3 的 `nav.xhtml`（`<nav epub:type="toc">`，层级用 `<ol>` 嵌套深度算）优先，EPUB2 的 `toc.ncx` 兜底（`<text>` 与 `<content src>` 顺序配对）；都没有就退回「每节取首个 h1~h3」，至少能跳。同一节的重复目录条目只留第一条
- **换字号 / 换主题不丢位置**：srcDoc 重建会让 iframe 重载，重载后按改动前的节内比例落回去
- **主题色从 CSS 变量读**：iframe 拿不到父文档的变量，直接 `getComputedStyle` 读 `--r-bg/--r-ink` 再写进 srcdoc，避免在 TS 里再抄一份色值（抄一份就一定会漏改）
- 冒烟新增 `[27]` 61 项（小节定位往返、加权进度与反算、nav/ncx 解析、沙箱剔除、纯图小节权重、缺失资源占位、大小写不一致的图片路径、真实 zip 构造的 EPUB 打开与按节取正文、越界/非 EPUB/损坏文件各自抛错），合计 **403 项**
- 渲染层实测（系统 Edge + playwright，脚本 `scripts/verify-epub.js`）：**37 项全过**（两本真实书各跑一遍）—— 一节接一节地滚、窗口自动前扩且有上限、滚轮与键盘转发、目录跳转落点精确、副标题跟着换章、改字号后位置不跳、中途退出重开落回同一处（42% → 第 52.45 节 → 42%）、一路滚到 100%、页面 0 报错 0 额外请求

## R4-a 已实现（书签 + 阅读时长）

阅读器本身能用了，这一轮补的是「读的过程里会想做的事」：留个记号、知道自己读了多久。

- **书签与进度是两套东西**：`reading_position` 是「上次读到哪」，一本一行、随时被覆盖；新增的 `bookmark` 表是用户主动留的记号，一本可以很多条。locator 复用同一套口径（TXT 偏移 / PDF 页号 / EPUB 小节），所以跳转不需要另写换算
- **同一位置重复加只更新不新增**：主进程按 `book_id + locator` 判重，渲染层在点下去之前先查一遍并提示「这个位置已经有书签了」。快捷键连按、从两个入口各点一次，都不会攒出两条一样的
- **列表按全书位置升序**，不是按添加时间——书签列表要跟阅读顺序一致，否则翻到第 5 条还得自己回忆它在哪

## R4-b 已实现（文内搜索）

读书时最常见的动作其实不是「翻页」而是「刚才那个词在哪儿」。这一轮把搜索做全了：三种格式都能搜、都能跳、都能看见高亮。

- **搜索放在主进程**，因为三种格式的「取文」方式根本不同：TXT 直接读全文按段落切（与阅读器同一套 `splitParagraphs`，偏移天然对得上）、EPUB 要遍历 zip 逐节 `htmlToPlainText`（一次解压全部小节、不内联图片）、PDF 要逐页 `getTextContent()` 再把文字项按行拼起来。渲染层只拿到统一的 `SearchHit`，不关心书是什么格式
- **统一的位置口径**：TXT 是字符偏移、PDF 是 1 基页号、EPUB 是 1 基小数小节位置（`52.45`）。跟书签、进度记录完全同一套 locator，所以「搜索跳转」不需要另写一套换算
- **摘要的偏移量不能靠猜**：换行和制表符要**逐字符**换成一个空格，不能压空白（一压 `hit_start` 就全错，高亮会歪到隔壁字上）；开头被截断时补的省略号也要算进 `hit_start`。这条在冒烟里用「反切摘要回原文」钉死
- **每一处命中都单独一条**，不按段落合并——同一段里这个词出现三次，就该看见三条，否则会以为只中了一次
- **大小写不敏感**先用 `toLowerCase()` 比长度：长度不变就直接 `indexOf`，长度变了（土耳其 `İ` 之类）才退化成逐位比较。直接对原串扫小写串会错位
- **结果上限 300 条**，超出时标 `truncated` 并在面板上说明。搜「的」这种字，全本命中几万处，全渲染出来只会卡死
- **取文结果按书缓存**：key 是「格式 + 文件大小 + 修改时间」，`MAX_CACHE = 2`。一本 500 页的 PDF 抽一次文字要好几秒，改了关键词再搜就该是纯字符串扫描。退出阅读器（`reader:setActive(null)`）时清空，不留内存
- **跳转后不关面板**：找词的人常常要连着看几处。`Enter` 下一处、`Shift+Enter` 上一处、到头折返，面板上的 `↑ / ↓` 是同一套逻辑；列表点一下也直接去。快捷键 `Ctrl+F`（`F3` 同样）打开，`Esc` 只关面板不退阅读器
- **高亮三套做法**（因为三种渲染方式没法共用）：
  - **TXT**：把命中段落切成三截插 `<mark class="reader-hit">`。**不加左右 `padding`**——多 1px 就可能提前折行，段落高度一变，虚拟滚动的位置就跳了
  - **PDF**：在文本层的 `span` 上按词匹配加 `.pdf-hit` 类。跨 `span` 的词只能标到其中一段，但跳转按页号走，落点一定准
  - **EPUB**：父窗口直接拿 `sandbox="allow-same-origin"` 那个 iframe 的 `contentDocument`，`TreeWalker` 找文本节点、`Range.surroundContents` 包 `<mark>`（单节点上限 40 处、从后往前包，避免节点被拆后偏移失效）。不重新解压、不重建 iframe
- **EPUB 落位先按「标」再按「比例」**：`scrollToMark` 用 `<mark>` 的真实 `rect` 把命中顶到视口上方 96px，拿不到才回落到 `scrollToSection(比例)`。按比例滚在长节里可能差半屏，按标记滚是像素级
- **iframe 里的高亮样式必须写进 `BASE_CSS` 且 `!important`**：主题里那条 `body * { background-color: transparent !important }` 会把底色抹成透明（实测拿到 `rgba(0,0,0,0)`）。这条不写死，界面上就是一排「看不见的高亮」
- 冒烟新增 `[31]` 24 项（摘要反切、换行不偏位、大小写、每处一条与顺序、空查询、上限截断、HTML 转纯文本、真 TXT 与真 EPUB 搜索），合计 **459 项**
- `verify-txt.js` 扩到 **56 项**：Ctrl+F 聚焦、空面板提示、同段重复三次就列三条、自动跳到 95%、跳转后面板不关、288 处命中、`1 / 288`、`Enter`/`Shift+Enter` 前后步进、点第 21 条、搜不到提示、`Esc` 关面板并清高亮

## R4-c 已实现（划线批注）

选中一段正文就能划线，顺手能写一句批注。三色（黄 / 绿 / 蓝）、一本多条、按阅读顺序列出、点了能跳回去。

- **锚点不用「原文 + 第几处」，用「拼接串上的字符区间」**。这是这一轮唯一真正需要想清楚的东西：
  - TXT：整本正文那个字符串；
  - PDF：某一页文本层**叶子 `span`** 的文本按顺序拼接（pdfjs 会给 marked content 再套一层 `span`，不取叶子会把文字算两遍）；
  - EPUB：某一节 iframe 里**所有文本节点按文档顺序**拼接。
  拼接串在插 `<mark>`、拆文本节点、`normalize()` 合并之后**长度与内容都不变**，所以偏移量跨会话稳定。反过来，如果按「第几个文本节点 + 节点内偏移」存，插一条高亮就会把后面全推偏；按「原文 + 第几处」存，每加一条高亮都要重新数一遍，越数越容易错
- **选区的偏移量靠 Range 算，不读 `startOffset`**：段落里插了 `<mark>` 之后 `startOffset` 是相对那个文本节点的，跟段落坐标对不上。做法是「从容器开头到端点的 Range 取 `toString().length`」；EPUB 里更省事——`cloneContents().textContent.length` 就是「这段范围里所有文本字符数之和」，与拼接口径天然一致
- **切片逻辑三种格式共用**（`shared/annotation.ts` 的 `sliceRuns`）：把 [起点, 终点) 按「所有区间的端点」切成互不重叠的片段，每片记下「谁覆盖了它」与「最上层是谁的颜色」。片段数量只跟区间数有关，与段落长度无关，TXT 一个几千字的段落也只切几刀
- **搜索高亮是「优先级更高的临时区间」**：混进同一套切片里，优先级高的赢。这样「划线上面又要盖搜索高亮」不用写第二份拆段代码。叠色时同优先级取后加的（id 大的），跟「后划的盖住先划的」直觉一致
- **相邻同色也不合并**：两条独立批注挨在一起时保持两截，否则点上去分不清该打开哪一条（冒烟专门钉住这条）
- **EPUB 的包裹从后往前做**：`surroundContents` 会把文本节点拆成三截，先处理靠后的区间，前面那些区间的节点引用与偏移才不会被挤偏。样式同样必须写进 iframe 的 `BASE_CSS` 且带 `!important`（主题那条 `body * { background-color: transparent !important }` 会把底色抹掉）
- **PDF 用 class 而不是包节点**：在叶子 `span` 上加 `.pdf-anno` 与颜色类，一个区间跨几行就标几个 `span`，不碰 DOM 结构，重新渲染也不会错位
- **选区在 iframe 里，父窗口收不到 `mouseup`**：EPUB 里由挂进 iframe 的监听器把「锚点 + 原文 + 视口矩形」送回父窗口。转换只加 `iframe.getBoundingClientRect()`——iframe 内部不滚动（`overflow:hidden`、高度=内容高），内容坐标就是它自己的视口坐标
- **交互刻意压到一次点击**：选中 → 弹浮层（摘录 + 三个色点 + 输入框）→ 点颜色即落库。想写批注就先打字再点色点，`Ctrl+Enter` 也保存。点已有的划线进同一个浮层，能改色、改批注、删。`Esc` 只关浮层不退阅读器
- **浮层位置夹在视口内**：贴在选区下方，下方放不下翻到上方，再夹一次边界。极端情况（选区在视口外）也不会把浮层顶出屏幕
- **从抽屉跳转要落两次**：`goTo` 只能落到「容器顶」——TXT 是段落顶、PDF 是页顶、EPUB 是节顶；划线在这一段/一页/一节的靠后位置时，跳完还在屏幕外，看着就是「跳错了地方」。所以跳完还要按 `<mark>` 的真实 rect 精修到视口上方 96px（与搜索命中同一套落位习惯）：EPUB 挂进原有的 `target`/`attempts` 重试链路（等 iframe load + 打标），TXT / PDF 用 rAF 重试，试满就放手，不跟用户抢滚动
- 冒烟新增 `[32]` 45 项（锚点编解码与脏值兜底、区间切片 6 种情形、拼接串分段、CRUD、同位置去重、非法锚点拒绝、级联删除），合计 **504 项**
- `verify-txt.js` 扩到 **79 项**：造选区 → 浮层 → 点色点落库 → 锚点是 TXT 口径 → 划线出现且底色非透明 → 点划线进编辑态 → 改色带批注 → 抽屉列出 → **滚走后从抽屉跳回来仍精确停在划线本身（视口上方 96px）** → 删除后正文一起消失 → `Esc` 只关浮层
- `verify-epub.js` 扩到 **69 项**：iframe 里造选区 → 跨文档送回父窗口 → 锚点是 EPUB 口径且落在当前节 → 划线真的打进 iframe 的 DOM（`rgba(232,178,74,0.44)`）→ 滚动换窗口后还在 → 点划线开编辑 → 删除后清零 → **节内偏 748px 的划线，从抽屉跳回来落在 96px（不是节首）**

## 修：加入书单选不到 + 评分移出编辑表单

两个操作层的问题一起处理。

**「有书单却选不到」**：

- **根因零（真凶）：StrictMode 下弹窗永远空白**。`main.tsx` 包了 `<StrictMode>`，开发模式 React 会把每个组件挂载两次（effect → cleanup → effect）；而弹窗的加载逻辑带了个「只加载一次」的 ref 守卫——第一次 effect 发请求并置位，cleanup 作废结果，第二次 effect 因已置位直接返回不再发请求 → `setLists` 永远不执行，弹窗一片空白。**生产构建不会双重执行，所以 playwright 实测全绿、用户 dev 必现**——「测试全过但真机炸」的经典案例。修法：删掉 ref 守卫。这两个弹窗本来就是条件渲染（关即卸载、开即重挂），重开天然重新加载，守卫纯属多余；`alive` 只用来防竞态。给所有弹窗式加载立了铁律：**条件渲染的弹窗里禁止「只加载一次」守卫**
- **根因一：静默失败**。`AddToListModal` 原来 `Promise.all([list.list(), list.forBook()]) + catch(() => {})`，任何一个请求挂掉，弹窗就是一片空白——书单明明存在却什么都选不到。现在两个请求**独立容错**：列表加载失败给 toast 和面板内提示（还能新建书单），预勾选失败只少勾选状态不碍事
- **根因二：加书只有详情页一条路**。书单页此前只能「移出书单」不能加，想往一个空书单里圈一批书得一本本点进详情。现在书单页标题栏有「**添加图书**」选书弹窗（`BookLists/AddBooksModal.tsx`）：列书架全部图书、搜书名/作者/标签过滤、勾选即加入、再点即移出、显示已选计数；勾中的行有高亮。详情页弹窗同步加了 `list-check-on` 高亮

## R4-d 已实现（跨页划线自动拆分）

**PDF 跨页划线**：一页一个坐标系，跨页选区在保存时按页自动拆成多条——起页从选区起点到页尾、中间页整页、止页从头到选区终点。多条同色同批注，各自独立可点可删可跳转，落库后 toast 提示「已划线（跨页已拆成 N 条）」。拆分逻辑是 `shared/annotation.ts` 的纯函数 `splitCrossPage()`（起止页码 + 各页拼接串长度 → 每页片段），同页退化为一条；任何一页还没渲染（拿不到文本层）、页码逆序、空区间一律整体放弃，不会存半截。冒烟 `[35]` 9 项钉死（同页退化 / 相邻两页 / 三页含整页中段 / 止页空选区 / 页长未知 / 逆序 / 空选区 / 起页从 0 开始）。

## R4-d 已实现：MOBI / AZW3 应用内阅读

**自己解，不引依赖**（`src/main/reader/mobi.ts`，约 500 行）。原本判断「性价比太低」的地方在于 HUFF/CDIC，真正动手后发现核心只有三件事，且都有可对照的实现：

| 压缩方式 | 占比（本地 103 本实测） | 做法 |
|---|---|---|
| 1 不压缩 | 25 本 | 记录原样当文本 |
| 2 PalmDOC（LZ77 变体） | 67 本 | 自己解，指令五分支（见下） |
| 17480 HUFF/CDIC | 11 本（AZW3 居多） | 照 calibre `mobi/huffcdic.py` 移植（256 项首字节表 + 32 级 mincode/maxcode + CDIC 短语字典，短语本身还是压缩流要递归解） |

**分节直接复用 EPUB 那一套**：一节一个 srcdoc iframe、外层滚动、进度按字数加权、书签/搜索/划线共用同一 locator。所以阅读器里没有「MOBI 分支」——只把 `=== 'epub'` 的判定换成 `isSectionFormat()`，三格式走同一条链路。

**拆节策略**：`<mbp:pagebreak>`（MOBI7）或 `<div data-AmznPageBreak>`（KF8，先归一成 mbp 再拆）→ 没有就按 `h1/h2` → 再没有按段落补切到 16000 字上限。**顺序不能反**：`sanitize` 会删掉 `<mbp:pagebreak>`，先洗后拆就永远只有一节。

**AZW3 = KF8 的三个特殊处**：

1. 合订本里 MOBI7 与 KF8 之间夹一条 `BOUNDARY` 记录，KF8 的 record 0 在它后面；EXTH 121 能给序号，给不了就扫记录找 `BOUNDARY`
2. 正文要按 `FDST` 记录的 flow 切开：flow 0 是正文，flow 1..N 是外挂 CSS（收进 `css` 字段，否则整本变成一个字体一坨黑字）。FDST 的序号是相对 BOUNDARY 编的、各家不一致，改成从正文之后顺序扫 `FDST` 魔数
3. KF8 常是**骨架文档**：`<body aid="0"></body></html>` 是空的，正文以 fragment 形式挂在 `</html>` 之后。`bodyInner()` 发现 body 里没字时改从 `</head>` 之后整段取

**踩过的坑（都是实测撞出来的）**：

- **PalmDOC 的 `0xC0-0xFF` 是「一个空格 + 一个字面量」**（字面量 = `c - 0x80`），不是「补 `c-0xC0` 个空格」。按后者写，真书里每个 `t`/`o`/`C` 都会变成一片空白：`<?xml version="1.0"` 读成 `<?xml` + 54 个空格 + `ersion="1.0"`，`xhtml11` 读成 `xTD  11`
- **MOBI 头偏移按 `'MOBI'` 起点算**（wiki 上那张表是按 record 0 起点算的，差 16 字节）：`0x5C` 首图记录号、`0x60/0x64` HUFF 表起止、**`0xE0` 文本记录尾部附加数据标志位**。`0xF2` 看着像（读到 0xFFFF）但那是 DRM 区，照它剥会把正文剥穿
- **`0xC0` 是 FLIS 记录号，不是 FDST**；KD8 的 FDST 编号基准各版本不一致，扫魔数最稳
- **文本记录尾部挂附加数据**（每条约 9 字节，KF8 约 43 字节）：长度写在末尾字节里，是**反向变长整数**，必须在解压前按字节剥。判据很硬——剥对了，各记录解压总长与 PDA 头里的 `textLength` **一比一相等**（实测 774226 = 774226，差 0）
- **`<head>` 里的 `<title>未知</title>` 会跑到正文顶上**：必须取 `<body>` 内层，不能整份文档塞 iframe
- **标题常是「主标题 + 序号」挤在一个 h2 里**：`奥斯曼：帝国的碎片` + `第一章` 直接拼会读成「…碎片第一章」，认出来就换位成 `第一章 · 奥斯曼：帝国的碎片`；标题里的 `<br/>` 当空格（`贝鲁特<br/>卡萨布兰卡的影子`）

**性能**：MOBI 没有「按节随机读」——要第 7 节也得把 190 条压缩记录全解一遍。阅读器一次取 6 节、搜索又要全量，所以整本解析结果按 `path + size + mtime` 缓存 2 份（大书冷启 1.8 秒，命中后取节 0 开销）。

**验证**：

- 真书全量：本地书库 **103 本** 全过（77 MOBI + 26 AZW3），含 11 本 HUFF/CDIC；输出无控制符残留，章节名、书名、节数、字数都正常
- 冒烟 `[38]` **29 项**：PalmDOC 五个指令分支（含 `0xC0-0xFF` 与重叠回溯的回归）、尾部附加数据长度、四种拆节路径、`bodyInner` 的骨架文档分支、坏文件抛错，以及「造书 → inspectMobi → readMobiSection → openForReading → readSection」整条链路

## P4 已实现：界面主题与书架卡片尺寸

侧栏底部「数据与备份」上面加了三个按钮：**浅色 / 深色 / 跟随系统**（默认跟随系统）。书架工具栏多了一组 **紧凑 / 标准 / 宽松**。

**主题为什么这么做**：

- **只是换一组变量**。`global.less` 里 `:root` 是浅色，`:root[data-theme='dark']` 是深色，页面样式一行没改——前提是页面不写死颜色。全项目 146 处硬编码色里 89 处都在 `Reader.less`（那边本来就有三套主题），页面层真正要改的只有几处语义色。
- **深色不是把浅色反相**：底色 `#191816`、卡片底 `#24231f` 都留了暖调，否则「暖纸质感」这个基调就丢了。
- **`--on-accent` / `--on-danger`**：白字压在暗金 `#b08d57` 上只有 3:1，深色主题换成近黑（8:1），顺带更像块铜牌。所有「强调色/危险色填充 + 文字」的按钮统一走这两个变量。
- **跟着系统走要主进程参与**：`nativeTheme.on('updated')` 变化时广播给渲染层；模式存 `settings` 表（不是 localStorage）——窗口底色要在**创建前**定下来（`backgroundColor: themeBackground()`），那一刻主进程读不到渲染层的 localStorage。底色与 `--bg` 必须一字不差，否则启动能看到一条色差。
- **首帧不能白闪**：preload 用一次 `ipcRenderer.sendSync('theme:initial')` 取当前结果，`main.tsx` 在 `createRoot` **之前**把 `data-theme` 打上。这是全项目唯一一处同步 IPC，换的就是「首帧就是对的颜色」。
- **`color-scheme: dark`**：原生下拉框、滚动条、选中框跟着变，不然深色界面里弹出一个白下拉。

**卡片尺寸**：`.shelf-grid` 的列宽下限走 `--card-min`（118 / 148 / 186），封面靠 `aspect-ratio: 3/4` 自己长高。选择存 `localStorage['shelf.cardSize']`，跟书架/列表视图一个路子；控件只在网格视图下渲染——列表里没有卡片，摆着就是个假按钮。

**阅读器背景也跟着走**：Aa 面板里「背景」从三档变四档，头一档是**跟随**（默认），界面浅色落纸白、界面深色落夜间，选中状态、TXT / PDF / EPUB 三种格式一起生效。

- **不让它俩共用一套色**：界面是「用一下就走」的，纸页是「盯两小时」的。界面那套 `--bg: #191816` 是 UI 灰，铺满整屏当纸页偏冷；`--r-bg: #1b1a18` 的夜纸是单独调过的。所以「跟随」只搬「选哪一档」，不搬色值。
- **`'auto'` 不落到 class 上**：`resolveReaderSkin(skin, ui) → 'paper' | 'night'` 这一步在 `shared/theme.ts` 里，`Reader` 拿到的永远是三选一，`.reader-theme-auto` 这种半成品类名根本不存在。EPUB 的 iframe 文档也是拿解析后的值重拼，否则「跟随」切档时 iframe 里还是旧底色。
- **界面主题走 prop 不走 `document`**：`App` 把 `theme.resolved` 传进 `Reader`。系统外观在阅读中途变了，主进程广播 → `App` setState → 阅读器跟着重渲染；要是去读 `html.dataset.theme`，那是命令式写进去的，React 不会因此重渲染。
- **存量迁移做一次，靠版本号不靠标记**：加「跟随」之前 `paper` 是所有人的默认值，存量里几乎都不是主动选的，所以 v1 的 `paper` 迁成 `auto`。版本号 `v` 存在 prefs 同一个对象里——早先试过独立的「已迁移」标记，它在模块加载时写、迁移却等到进阅读器才跑，中间关一次程序就成了「标记落了、值没落」，之后永远迁不动（本机真踩到）。现在判定在 `loadPrefs` 里做、值与版本一起写回，两遍执行结果也一致（StrictMode 安全）。之后用户自己点「纸白」会被原样保存。

## 阅读统计（新增页面）

侧栏「全部图书」下面多了「阅读统计」。四档范围（近 7 天 / 近 30 天 / 今年 / 全部），一页给全：核心数字、全年热力图、按天或按月的趋势、星期分布、格式 / 分类 / 标签占比、读得最久的书。

**口径是硬的**：

- **时长只有天粒度**：`reading_session` 一本一天一行，所以画不出「几点到几点在读」。要小时级得改成会话明细表，那是另一件事（见已知边界）。
- **只算真读的时间**：窗口不可见、失去焦点、连续 5 分钟没翻页都不计，所以数字会略低于「窗口开着的时间」。
- **用活跃日均，不用自然日均**：总时长 ÷ 有记录的天数。停读三天不该把日均拉成 5 分钟。
- **连续阅读按全量历史算**：区间只影响「这段时间读了多少」。而且**今天还没读不算断**，否则每天早上打开都是「连续 0 天」，昨天攒的全白扔。
- **分类合并到顶层**：三级分类各画一条会变成一屏长尾。未分类单独一组——它是「还没归类」，不是没数据。
- **标签是多对多**：一本书挂两个标签，两个标签各记一遍它的时长，所以这一列加起来会大于总时长。界面上直接写了这句，否则看着像算错。
- **格式按文件扩展名**：不用 `reading_position.format`——那只在应用内读过才有值。

**图表是手写的**：柱状 / 热力 / 水平条三种形状全是 CSS grid + flex，没引图表库（整页只有三种形状，为此塞 1MB 的 ECharts 不划算，每根柱子挂个 `title` 就够说清是哪天读了多久）。

**几个坑**：

- **日期算术一律不碰 `toISOString`**：它是 UTC，东八区晚 8 点后会把日期算成第二天，而 `reading_session.day` 是本地日。全部走 `localDate()` / `shiftDay()`。
- **「全部」按天画会挤成一条线**：粒度由范围决定（7d / 30d 按天，year / all 按月），判断在 `granularityOf()`，后端取数与横轴标签共用一份。
- **横轴必须补空**：后端只回有数据的天，`fillDays` / `fillMonths` 把空档补 0——少一格，柱子就整体错位。
- **热力图不跟范围走**：它回答的是「这一年读得勤不勤」，切到近 7 天也该看全年。格子起始日推到周一，否则每列会被切碎。
- **0 值不画柱子**：`min-height: 2px` 是为了让「有值但很小」的日子可见，0 的那天会变成一条细线，被读成「读了一点点」。
- **两个空状态要分开**：一条记录都没有 → 引导页；只有几分钟 → 顶部加一句「记录还很少」，否则满屏 0 很像坏了。

**验证**：

- 冒烟 `[40]` **46 项**：纯函数（日期进位与闰年、四档区间起点、星期口径、连续天数四种情形、补空、跨年按月、时长文案边界、除零、Top N 合并、热力图整周）+ 真库聚合（区间外不算、空缺补 0、分类顶层合并、未分类、标签重复计、格式、书榜排序与 limit、读完/划线/书签/笔记计数、四档范围、空表不炸）
- 渲染层 `verify-stats.js` **32 项**：入口可点、默认档、四档切换真的换数（KPI / 柱数 / 副标题 / 横轴格式一起变）、热力图整周且带月份标尺、趋势柱数、横轴标签不超过 6 个、星期固定 7 根、三组占比条、书榜点名次、点书榜进详情、深色无大片纯白、空库引导、数据极少时的解释条

## 书架批量操作

多选后一次性**改阅读状态 / 加标签 / 摘标签 / 改分类 / 移入回收站**。

- **入口**：书架工具栏的「选择」。进去后卡片左上出勾选圈、列表首列出勾选框，同时把筛选 / 排序 / 卡片大小收起来——动任何一个都会清空已选，摆在那儿就是三个「一点就白选」的陷阱。
- **点选语义**：普通点击＝切换这一本（要一个个勾时不用按 Ctrl）；`Shift` + 点击＝从锚点连选一片，**只加不减**（取消一片交给全选/取消）；「全选」只作用于当前列表（筛选后的结果）；`Ctrl/⌘ + A` 全选，`Esc` 先关面板、再按一次退出。
- **一次事务**：`book:batch` 一个 IPC 带 `{ kind, ... }`，主进程 `repo.batch.ts` 里 `db.transaction` 包住全部写入，中途报错整批回滚。写入是**逐本一条语句**而不是 `IN (...)`——SQLite 老版本绑定参数上限 999，「全选」很容易上千本，一条 IN 直接报 too many SQL variables。
- **标签是「加 / 摘」，不是「设为」**：批量覆盖会把每本书原有的标签全清掉（给 20 本加个「待读」，结果 20 本只剩「待读」）。`tag_add` 走 `INSERT OR IGNORE`，`tag_remove` 只删点名的那些，其它原样留着。`cleanNames()` 单独导出，批量不套用「每本最多 20 个」那条覆盖式约束。
- **状态跃迁走同一份副作用**：`applyStatusChange()` 从单本 `update()` 里抽出来，批量改状态也调它——否则「批量标已读」写了时间线却没补 `finish_read_at`，详情页就少个读完日期。
- **跳过不算错**：列表可能是几秒前的快照，已经进了回收站的 id 计入 `skipped` 不当失败；全都跳过时提示「这些书都不在架上了」。
- **操作完不闪**：批量落地会 `bump()` 刷新，而 `Shelf` 的 key 里**不再放 dataVersion**——放了就整页重建，「加载中…」闪一下再回来，反倒让人以为刚才那步没生效。改成只有首次进入才显示加载态。
- **选择模式收起「阅读 / 打开」角标**：一张卡上两个可点目标，手一抖就成了「想选中却把书打开了」。

**验证**：

- 冒烟 `[41]` **25 项**：五种动作在真库上的结果、重复标同一状态不重复写时间线、标签追加不破坏原有标签、标签名清洗（去空白/去重/丢弃空名）、摘不存在的标签静默成功、分类不存在时整批不动、已在回收站的计入 skipped、空/脏 ids 报错、重复 id 只处理一次、未知 kind 报错

## 详情页宽屏三栏（右栏：页内跳转 + 同类书）

`.page-detail` 原本是 `max-width: 980px` 的两栏（封面 240 + 正文）。1280 的默认窗口里内容区只有 1004，980 几乎铺满，看着没问题；**一旦最大化到 1920，内容区 1644 而页面只占 980，右边空 660 多像素，整页重心压在左边**。

- **断点 1480px 换成三栏**：`240px minmax(0, 1fr) 260px`，`max-width: 1400px` + `margin-inline: auto`。
  - 断点不是随手取的：再窄一点正文列就掉到 650 以下（原来 708），加一栏等于把问题换成「正文被挤窄」。
  - `minmax(0, 1fr)` 不能写成 `1fr`——长书名 / 长文件名的 `nowrap` 会把列撑破。
- **右栏 sticky**（`top: 8px`）：详情页很长，滚到「摘录」时还能一眼跳回「简介」。
- **页内跳转的标题从 DOM 现拿**（`h2` 文本），不另写一份清单：以后加删区块，目录自己跟上，不会两处各说一套。
  - 跳转用「相对滚动容器的偏移」而不是 `scrollIntoView`——后者会把外层窗口也带着滚；差值再减 12px 留白。
  - 高亮用「最后一个越过顶线的区块」，不是 IntersectionObserver：多个区块同时在视口里时，读者要的是正在读的那块。
- **同类书**：同分类优先，不够 3 本再用同作者（`book.list` 的 `categoryId` / `keyword`，无需新 IPC），自己排除；查不到整块不渲染。点进去要**手动把滚动容器归零**——detail → detail 是同一个组件实例，不归零会停在上一本的半腰。
- **无封面的同类书用首字 + 渐变兜底**，和书架卡片同一个路子，不至于裂成一块白。

**验证**：`verify-detail.js` **23 项**（1920 下右栏出现 / 真的不重叠 / sticky / 整页左右留白相等 / 正文列不被挤窄 / 目录与区块一一对应 / 点目录滚到位且高亮跟着走 / 滚回顶部高亮复位 / 同类书 3 本且不含自己 / 点同类书换书并回顶 / 1280 右栏消失且版心退回 980 / 深色下右栏不是白牌）。

## 摘录卡片（划线 → 图）

把阅读器里划的线排成一张能存、能发的图。**纯本地 canvas 绘制**，不上传、不联网、不引图表库。

- **两个入口**：详情页「摘录与批注」头部的「做成卡片」（整本一起）和每条划线右侧的「做成卡片」（只要这一条）。
- **三档尺寸**（方图 1:1 / 竖版 4:5 / 长图 9:16）+ **两档底色**（纸白 / 墨黑，默认跟界面主题走）。
- **档位先保比例，再谈高度**：内容装不下时先把整版字号等比缩小（行高、块间距一起，图宽不变），二分找到「刚好装得下」的最大字号，下限 `CARD_SCALE_MIN = 0.62`（44px 正文缩到 27px，手机上仍清楚）。缩到下限还装不下，才让图长高——宁可出一张长图，也不把你摘的句子截掉。两种妥协都会在侧栏明说（「字号已缩到 83%」/「缩到最小字号仍放不下，图已自动加长到 1141，比例不再是 1:1」）。
  - 早先只有「高度 = max(档位高, 内容高)」一条规则，结果两档都长到同一个 1715，方图 1:1 名存实亡——档位就等于没生效。
  - 二分出来的 `scale` **只用于显示**，排版必须用它本身重排：`toFixed(3)` 往上四舍五入会跨过一条折行边界，多一行就把高度顶出档位（实测方图从 1080 变 1141）。断行对字号是跳变的，别让「取整」反过来改版式。
- **留白大时内容整体居中**：只有日期贴底。不然一张 9:16 的图里文字全挤在顶上、下半张空得发慌。
- **版式是纯函数**（`shared/card.ts`）。断行需要量字宽，而主进程没有 canvas，所以**测量函数是注入的**：渲染层传 `ctx.measureText`，冒烟传「中文一字宽 = 字号、ASCII 半字宽」的假测量。断行、超长英文词硬切、行尾空格、最小高度、居中偏移全都能脱离浏览器断言。
- **断行按不可拆单元切**：连续 ASCII 单词算一个整体（不把 `apple` 劈成 `app` + `le`），中文逐字，空格单独一个单元且行首丢弃；单个词就超宽时按字符硬切。
- **保存 / 复制交给主进程**：`card:save` 走 `dialog.showSaveDialog` 写 PNG（文件名 `书名-摘录-20261028.png`，非法字符清掉、按字截断到 40 字）；`card:copy` 写系统剪贴板。Electron 44 的 `clipboard.writeImage` 已经没了，改用 W3C 那套 `new ClipboardItem({ 'image/png': new Blob([...]) })` + `clipboard.write([item])`。
- **顺手补了书签备注入口**：`bookmark.note` 与 `updateNote` 早就有、界面一直没地方用。现在书签抽屉里每条下面多一行「＋ 备注」，点一下原地变输入框，`Enter` 保存、`Esc` 取消（`stopPropagation` 拦住，不然 `Esc` 会冒到窗口把整个抽屉关掉）。

## 已知边界（有意取舍，后续再议）

- **PDF 封面只取首页第一张内嵌位图**：矢量绘制的封面（无内嵌图对象）提取不到，会用书名渐变占位；这是不引 canvas 原生模块换来的轻量，个人规模够用
- MOBI 封面取 firstImageIndex 起的第一个含 JPEG/PNG magic 的 record，个别打包不规范的文件可能取错
- 扫描 / 导入过程在主进程顺序执行，数百本 PDF 的目录要等十几秒（UI 不卡，IPC 是异步的）；超大目录后续可加分批 + 进度事件
- 封面裁剪交互未做：目前只做上传 / 替换 / 移除；压缩固定长边 720px（`utils/cover.ts` 的 `compressImageFile`），个人规模无需缩略图缓存
- 标签筛选走客户端过滤（当前分类/关键词结果集已在内存），万本以上规模可下推 SQL
- 中文书名排序走 SQLite 二进制排序（非拼音序），个人规模可接受；量大可上 FTS5 + 自定义 collation
- **应用内阅读支持 TXT / PDF / EPUB / MOBI / AZW3**：TXT 上限 15 MB（虚拟滚动后还能往上抬，但整本过 IPC 与解码的成本会开始明显），PDF 上限 512 MB，EPUB / MOBI 上限 256 MB
- **PDF 的整份字节是经 IPC 交给渲染层的**：几十 MB 的书感觉不到，几百 MB 的扫描件打开会明显占内存（峰值约文件大小的两三倍）。真要伺候这类文件，得改成自定义协议按 Range 流式读取，这一轮没做
- **PDF 夜间模式只压亮度不反色**：反色对图文书很难看，扫描件本身是白底，压到 0.84 亮度已经够用
- **EPUB 的滚动窗口只留 6 节**（前 2 后 3，并集上限 12）：超长的一节（实测有 4.9 万像素高）全靠一个 iframe 撑，Chromium 单个 iframe 到这个量级还稳，再长就该改成分段渲染
- **关窗确认只认「阅读器里」**：主进程只在 `reader:setActive` 报了书名时拦一道。从书架或详情页关窗口仍然是直接退出——那里没有「读到一半」的状态需要保
- **EPUB 的 CSS 只做「能读」**：整份内联但会强制覆盖 `html/body` 的字号、行距、颜色与所有元素的 `background-color`（不覆盖的话书里写死的浅底/深字在夜间模式下会瞎）。代价是个别书的背景图片装饰会被抹掉
- **MOBI / AZW3 的两个边界**：① 一本 39 MB 的合集（诺贝尔文学奖大系）冷启要解 1.8 秒，越大越慢——整本解压是格式决定的，缓存只能省掉重复；② 划线锚点在库里仍记作 `k: 'epub'`（分节格式共用一套锚点编码），改名会让已有划线全部失效，故保持不动，只当它是「分节口径」的标记
- **摘录卡片不出封面/图片**：整张图只有字与一条强调色短横线。加封面要异步取图并参与版式计算（纯函数就得变成异步），第一版没做
- **卡片一次只排一本书**：跨书的「主题摘录集」还做不了
- **阅读时长按天聚合，没有会话明细**：只能回答「哪天读了多久」，画不出「几点到几点在读」；后台 / 无焦点 / 5 分钟无交互不计时，所以数字会略低于「窗口开着的时间」，这是有意的。统计页的趋势曲线因此最细也只到「天」，想要小时热力得先有会话表（每天几行数据，几十万行起步）
- **书签只在阅读器里管**：备注能写了（抽屉里就地编辑），但详情页仍看不到这本书有几条书签，也没有「清理无用书签」的批量操作，个人规模够用
- **TXT 目录靠正则猜**：没有「第 X 章」这类行首标题的流水文本不会生成目录，但正文与进度记忆不受影响
- **文内搜索的几个边界**：① 只搜当前这本书，不做书库级全文检索（那要 FTS5 索引，是另一件事）；② 不提供「全词匹配 / 正则 / 区分大小写」这些选项，输入什么就按不区分大小写找什么；③ EPUB 首次搜索要把整本解压一遍（几 MB 的书 1~2 秒），之后同大小同 mtime 直接命中缓存；④ PDF 扫描件没有文本层，搜不到任何东西——这不是 bug，得先 OCR；⑤ PDF 的高亮只能标到单个文本层 `span` 内，跨 `span` 的词会标不全，但跳转按页号走，落点仍然准
- **搜索命中上限 300 条**：超出会在面板上提示「结果过多，只显示前 300 处」。搜常见字时这不是限制而是保护，真要看全就得往 FTS5 走
- **划线批注的几个边界**：① 一条划线只在同一「块」里有效——TXT 是整本所以随便跨段，EPUB 一条不能跨节、PDF 跨页选区直接忽略（一页一个坐标系，跨页得拆成两条）；② 换字号 / 改版心之后位置不会漂，因为锚点是拼接串偏移而不是像素；③ 但**换文件**就会错——把 EPUB 重新打包、或者换成同名不同版本的书，锚点会指到别的字上，这是所有「按文本定位」方案的共同代价；④ 划完只存在于阅读器里，详情页暂时没有「摘录与批注」入口
- **PDF 的划线没有渲染层实测**：跟文内搜索一样，手边没有合适的 PDF 样本能进 verify 流程，目前只有主进程逻辑与 TXT / EPUB 两条链的完整覆盖。计数、切片、锚点编解码是共用的，风险集中在「叶子 span 拼接」这一处；**抽屉跳转的二次精修也是这样**——TXT / EPUB 由 verify 钉住落点，PDF 靠同一套思路（`pageTop(页) + span 页内偏移 - 96`）推出来的，等有样本再补
- **批注不做富文本**：纯文本 + 三种底色。加粗、引用、图片会把「一句话的批注」变成一篇小作文，那是笔记该干的事
- **虚拟滚动的位置精度依赖估算**：没读过的区域用「字号 × 版心宽」估行数，中文正文误差通常 < 1 行；拖动滚动条首次跳到远处可能有 1~5% 的落点偏差，滚一屏后修正。段落高度无法预知是流式排版的天生限制，PDF / EPUB 有固定页或 CFI 就不受影响
- 包体：入口 chunk ~822KB（React 19 全量），PDF 相关三个 chunk（pdfjs 820KB / worker 1.09MB / cmaps 1.57MB）按需加载。桌面本地应用可接受
- 「未分类」没有独立侧栏入口，从「全部图书」进入
